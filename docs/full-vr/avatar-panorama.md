# 化身全景：一帧画面里拿到 360° 彩色和深度

bot 的两只眼原本只看到头显前方约 100°×100°，要看身后就得转头、拼多帧。这里的办法是：在 bot 的化身上放 6 台只在本地运行的相机（水平 4 台、上下各 1 台），各自渲染到一张 RenderTexture；再用一个 HUD 着色器把 6 个面原样拷进眼睛画面。**左眼是彩色全景，右眼是同样布局、逐像素对齐的深度全景。** bridge 本来就在截取两只眼的画面，拿一帧就得到整个球面的彩色和深度。

- 只有 bot 自己的眼睛看得到；别的玩家、镜子、拍照相机都看不到，别人的客户端也不运行这些相机。
- 平时关着，bridge 用 OSC 打开 `Pano`，拿到几帧就关（代价见第 6 节）。
- 每帧带一个元数据条码（与 PosBeacon 同格式，magic 0x5B），写着相机组的世界位置、朝向、布局编号和深度编码方式，bridge 不用猜。
- PosBeacon 照常画在左下角，两只眼都能读。

本文是**协议和实现说明**。化身端在 Avatar 项目（`E:\Project\VRChat\M3`）里实现，读码端在 bridge 里实现，两边都按第 3 节的格式。设计依据见 `research_notes/VRC 流式说话人与立方体全景/avatar_cube_pano.md` 和 `avatar_depth_light.md`。

## 1. 效果

- 打开 `Pano` 后，bot 每只眼的画面（1920×1920）被分成 7 块：
  - 上面两行是 4 个水平面，每个 960×720：第一行左是 rig 朝向 270°（左），右是 0°（前）；第二行左是 90°（右），右是 180°（后）。从左上往右下读，是连续的一圈：左、前、右、后。
  - 最下面一条（高 480）：左半边 960×480 是保留区（PosBeacon、元数据条码、标定格），右半边是向上（Up）和向下（Down）两个面，各 480×480。
- 左眼画彩色，右眼在同一位置画深度（E1C 编码，3.3）。右眼的像素 (x, y) 就是左眼像素 (x, y) 那条射线上的深度。
- 每帧都重画。相机和 HUD 在同一帧里先后渲染（相机的 depth 比眼睛相机小），第一帧之后画面就是当帧的。
- 不画的时候：
  - 别的玩家的客户端：相机和渲染器都不打开（只有 `IsLocal` 且 `Pano` 才开，见 2.1 第 7 步）；
  - bot 自己的客户端里：相机不在 rig 附近（`_OwnerRadius`），或者不是立体相机（我们自己的 6 台相机、VRChat 的手持相机都不是）；
  - 镜子（`_VRChatMirrorMode` 不为 0）；
  - 拍照、录像相机（`_VRChatCameraMode` 不为 0）；
  - 别人屏蔽了动画时，相机和渲染器停在默认的关；屏蔽了着色器时，回退规则设为隐藏（`VRCFallback = Hidden`）。

## 2. 化身端怎么做

### 2.1 物体

化身端已经实现，方式和 PosBeacon 一样：编辑器安装脚本 `Assets/xkeyC/PanoRig/Editor/PanoRigSetup.cs` 用 `PrefabUtility.LoadPrefabContents` 打开化身预制体 `Assets/M3/M3 Shinano.prefab`，改完 `SaveAsPrefabAsset`。RenderTexture、材质、网格、动画控制器和两个动画片段也由脚本生成，放在 `Assets/xkeyC/PanoRig/`；重复运行会更新已有的东西（RenderTexture 原地改格式，GUID 不变）。

菜单 `Tools/xkeyC/Pano Rig/` 下有 Apply (D1)、Apply (D2)（见 3.3）和 Run Tests；代码里是 `PanoRigSetup.Apply()`（默认 D1）、`PanoRigSetup.Apply(new PanoRigSetup.Options { ... })` 和 `PanoRigSetup.RunTests()`。`Options` 里的开关：

| 开关 | 默认 | 作用 |
|---|---|---|
| `Route` | `D1` | 深度来源：D1 纯深度相机，D2 深度灯 + 编码四边形（3.3） |
| `Nameplates` | 开 | 相机拍不拍 InternalUI(19) 层，也就是名牌。VRChat 里能不能拍到、朝向对不对没验证，不对就关掉重新上传 |
| `D2PlayerLocal` | 开 | 只在 D2 时有用：相机也拍 PlayerLocal(10)，让编码四边形有机会运行（7.4） |
| `DepthFormat` | `D32_SFloat` | D1 深度格式。`D16_UNorm` 是 IkeHUD 在 VRChat 里用过的格式，D32 在 VRChat 里还没用过（7.5） |

脚本做的事：

1. **锚点** `PanoAnchor`：Head 骨骼下的空物体，放在化身视点（Avatar Descriptor 的 View Position），跟着头走，也就是跟着眼睛走。
   - 第一人称会把 Head 和它下面的东西缩到接近 0，所以照 PosBeacon 的做法加 `VRC Head Chop`：目标是它自己，缩放系数 1，Apply Condition 选 Always Apply。化身上现在共 3 个 Head Chop（PosBeacon、IkeHUD、PanoAnchor），上限 16。
2. **rig** `PanoRig`：化身根的子物体（不放在 Head 下）。
   - `VRC Position Constraint`：源是 `PanoAnchor`，权重 1，**偏移为 0**，世界空间求解，Active 且 Locked。rig 的位置就是眼睛的位置。
   - `VRC Rotation Constraint`：源是 Head，**只影响 Y 轴**（X、Z 不影响，停在 0），世界空间求解。Head 骨骼的本地轴是模型自己的，所以旋转偏移设为"Head 静止姿态相对化身根的旋转"的逆（`PanoRigSetup.RestOffset`），静止时 rig 的偏航正好是 0。结果：**rig 始终水平，偏航等于头的偏航**（头的前方向在水平面上的投影，与俯仰、横滚无关；只有正上、正下看时不稳定）。
   - 为什么不跟化身根：VR 里化身根跟的是游玩空间，不是身体，更不是头（5.3）。
3. **PanoEye**：`PanoRig` 的子物体，本地位置、旋转都是 0。6 台相机和 HUD 都挂在它上面，它的世界位置和偏航就是条码里的"相机中心"和 rig_yaw。
4. **6 台彩色相机** `Cam_0`、`Cam_90`、`Cam_180`、`Cam_270`、`Cam_Up`、`Cam_Down`（`PanoEye` 的子物体，位置 0）。姿态和视场见 3.2。每台：
   - 渲染到自己的 RenderTexture `PanoFace_*.renderTexture`：水平面 960×720，上下 480×480；R8G8B8A8_SRGB（D2 时是 R16G16B16A16_SFloat）、D24S8、点采样、无 MSAA、无 mip、无 HDR。
   - near 0.05 m，far 100 m，Clear Flags 天空盒，Camera depth −50（比眼睛相机小，同一帧里先渲染），Target Eye None，Occlusion Culling 开。
   - Culling Mask：除了 PlayerLocal(10)、UiMenu(12)、StereoLeft/Right(15/16)、MirrorReflection(18)、HardwareObjects(20) 以外都勾（默认 `0xFFEA6BFF`，含名牌层 19）。**向下的相机也一样排除自己**，所以能透过 bot 自己的身体看到地面。
   - **Camera 组件默认关**（`enabled = false`），由动画器打开。
5. **深度**，按 `Route`：
   - D1：6 台纯深度相机 `Depth_*`，位姿、视场、宽高比、culling mask 都和对应的彩色相机一样，渲染到 `PanoDepth_*.renderTexture`（颜色格式 None，深度 D32_SFloat，尺寸和彩色面相同，所以逐像素对齐），Clear Flags 只清深度。默认关。
   - D2：`PanoEye/PanoEncoder`（编码四边形，渲染器默认关）和 `PanoRig/PanoDepthLight`（深度灯，组件默认关）。灯的配方取 IkeHUD 的 DepthEnabler：方向光、颜色黑、强度 0.001、硬阴影、阴影强度 0、只照第 2 层（Ignore Raycast）、Realtime。
6. **HUD**：`PanoEye` 上的 `MeshFilter` + `MeshRenderer`，材质 `PanoHud.mat`（着色器 `xkeyC/PanoHud`，6 张彩色面和 6 张深度图都连在材质上）。
   - 网格是 Unity 自带 Quad 的复制品 `PanoQuad.asset`，**包围盒放大到 1 m**，眼睛总在包围盒内，不会被视锥剔除（PosBeacon 文档 7.1）。四边形画在哪里由着色器决定。
   - Cast Shadows Off，各种 Probe Off，Force No Motion，Dynamic Occlusion 关，**默认关闭**。
   - HUD 不在 Head 下面，不需要 Head Chop。
7. **只在 bot 自己的客户端里打开**：Modular Avatar 合进 FX，做法和 PosBeacon 相同：
   - `MA Parameters`（挂在 `PanoRig` 上）：bool `Pano`，默认关、**不保存**、只在本地（不同步，不占同步位，OSC 照样能改）。
   - `MA Merge Animator`：FX 层，路径相对 `PanoRig`，跟随化身的 Write Defaults。层里两个状态：
     - `Off`（默认）→ `On`：`IsLocal` 且 `Pano`；
     - `On` → `Off`：`IsLocal` 为假，或 `Pano` 为假。
   - `On` 片段（长 10 s，不循环）：所有相机的 `Camera.m_Enabled`、HUD 的 `MeshRenderer.m_Enabled` 置 1（D2 时还有编码四边形和灯）；HUD 的材质属性 `_PanoAge` 从 0 线性涨到 10（秒）。`Off` 片段：全部置 0。
   - 别人的客户端里 `IsLocal` 恒为假，相机不会被打开；非好友那边相机组件直接被 VRChat 移除。
   - bridge 用 OSC 发 `/avatar/parameters/Pano` 打开或关掉。
8. 化身上的灯光控制工具（NyaPPu LightController）的排除列表里加上 `PanoRig`，同 PosBeacon 文档 2.1 第 5 步。

### 2.2 着色器

内置渲染管线，两个着色器都在 `Assets/xkeyC/PanoRig/`。写法照 PosBeacon：顶点里算好条码数据，`nointerpolation` 传给片元；单通道立体实例化（SPI）下用 `UNITY_VERTEX_OUTPUT_STEREO`、`UNITY_INITIALIZE_VERTEX_OUTPUT_STEREO`、`UNITY_SETUP_STEREO_EYE_INDEX_POST_VERTEX` 拿眼索引。

**`xkeyC/PanoHud`**（`PanoHud.shader`）：队列 Overlay+50（PosBeacon 是 Overlay+100，画在它上面），`ZTest Always`、`ZWrite Off`、`Blend Off`，`VRCFallback = Hidden`。

- 守卫（顶点里，不满足就把四边形扔出视野）：相机离 rig 不到 `_OwnerRadius`（0.35 m）、是立体相机（`USING_STEREO_MATRICES`）、`_VRChatMirrorMode == 0`、`_VRChatCameraMode == 0`。非立体相机一律不画，这一条挡住了"HUD 被自己的 6 台相机拍进面里"的反馈。编辑器测试时把材质的 `_EditorTest` 设为 1 才能在普通相机里画，`_EditorEye` 指定画哪只眼。
- 顶点里四边形铺满整只眼，和 PosBeacon 一样用 `ndc.y * _ProjectionParams.x` 处理翻转；uv (0,0) 是眼睛画面的左下角。
- 片元里按 uv 判断这个像素属于哪一块：

```hlsl
// i.uv: (0, 0) = the eye's bottom-left
if (i.uv.y < 0.25 && i.uv.x < 0.5) { /* reserved corner: PosBeacon (discard), code, calibration */ }
if (i.uv.y >= 0.25)
{
    bool top = i.uv.y >= 0.625;
    bool right = i.uv.x >= 0.5;
    face = top ? (right ? 0u : 3u) : (right ? 2u : 1u);  // 270 | 0 over 90 | 180
    f = float2(frac(i.uv.x * 2.0), (i.uv.y - (top ? 0.625 : 0.25)) / 0.375);
    size = int2(960, 720);
}
else
{
    face = i.uv.x < 0.75 ? 4u : 5u;                        // up | down
    f = float2((i.uv.x - (face == 4u ? 0.5 : 0.75)) / 0.25, i.uv.y / 0.25);
    size = int2(480, 480);
}
int2 t = min((int2)floor(f * size), size - 1);   // the face's texel, bottom-left origin
```

- 左眼：`_FaceN.Load(int3(t, 0))`，原样输出。**纯点拷贝，没有重采样**：眼睛画面是 1920² 时，块里每个像素正好对应面上一个像素。sRGB 面读出来是线性值，写进 sRGB 眼睛画面时硬件再编码回去，字节不变（编辑器里逐字节验证过）。
- 右眼：读深度（D1 读深度图，D2 读面的 alpha），换成米，再按 3.3 编码。所有纹理都用 `Texture2D` 加 `Load` 读，不用 `UNITY_DECLARE_DEPTH_TEXTURE`：那个宏在 SPI 变体下是纹理数组，会取错层。
- 保留区：PosBeacon 的矩形外扩一格 `discard`（不写任何东西）；条码画黑白方块；右眼的标定格画已知的深度级（3.5）；其余填黑。

**`xkeyC/PanoDepthEncoder`**（`PanoDepthEncoder.shader`，只有 D2 用）：队列 Overlay+400，`ColorMask A`，只改 alpha。

- 守卫：非立体、相机离 rig 不到 0.2 m、透视投影、投影矩阵正好是 rig 相机的两种之一（水平面 |P00| = 1、|P11| = 4/3；上下 |P00| = |P11| = 1/tan55° = 0.7002）、不是镜子和拍照相机。其他相机里都不画。
- 片元：按 `SV_Position` 取本相机自己的 `_CameraDepthTexture`，`LinearEyeDepth` 换成米（用的是这台相机自己的 `_ZBufferParams`），写进 alpha；什么都没画到（天空）写 65504。
- 前提：相机得有 `_CameraDepthTexture`，所以 D2 要开深度灯（`PanoDepthLight`），而且编码四边形得被这些相机拍到（7.4）。

## 3. 格式（两端的约定）

### 3.1 布局（layout 1）

坐标：眼睛画面 1920×1920，像素原点在**左上**，y 向下（bridge 拿到的图就是这样）。

| 块 | x | y | 内容 |
|---|---|---|---|
| 270 | 0..960 | 0..720 | rig 朝向 270°（左）的水平面 |
| 0 | 960..1920 | 0..720 | 0°（前） |
| 90 | 0..960 | 720..1440 | 90°（右） |
| 180 | 960..1920 | 720..1440 | 180°（后） |
| 保留区 | 0..960 | 1440..1920 | PosBeacon、条码、标定格（3.5） |
| Up | 960..1440 | 1440..1920 | 向上 |
| Down | 1440..1920 | 1440..1920 | 向下 |

- 每块就是对应相机的整张图，方向不变（块的上边就是相机画面的上边），块内像素 (i, j)（左上原点）= 相机画面像素 (i, j)。
- 左眼是彩色，右眼同一位置是深度。右眼保留区里多了标定格，左眼保留区里那些位置是黑的。
- 布局编号写在条码里（3.6）。以后改布局就换编号，bridge 只解认识的编号。
- 眼睛画面如果不是 1920²（VRChat 渲染比例不是 1 时），着色器按比例取最近像素，块的位置按比例缩放，但不再是 1:1 拷贝。bridge 发现眼睛尺寸不是 1920² 时要按比例换算，并知道细节会损失。

### 3.2 相机的位姿和内参

所有相机都在 `PanoEye`（条码里的位置），在 rig 坐标系（水平，+Z 是头的水平朝向，+X 右，+Y 上，Unity 左手系）里的本地旋转（Unity 欧拉角，先 Z 再 X 再 Y）：

| 面 | 欧拉角 | 画面中心看向 | 画面上方 | 画面右方 | 尺寸 | 视场 | fx = fy | cx, cy |
|---|---|---|---|---|---|---|---|---|
| 0 | (0, 0, 0) | 前 (+Z) | 上 | 右 (+X) | 960×720 | 水平 90°，垂直 73.74° | 480 | 480, 360 |
| 90 | (0, 90, 0) | 右 (+X) | 上 | 后 | 960×720 | 同上 | 480 | 480, 360 |
| 180 | (0, 180, 0) | 后 (−Z) | 上 | 左 | 960×720 | 同上 | 480 | 480, 360 |
| 270 | (0, 270, 0) | 左 (−X) | 上 | 前 | 960×720 | 同上 | 480 | 480, 360 |
| Up | (−90, 180, 0) | 上 (+Y) | **前 (+Z)** | 左 (−X) | 480×480 | 110°×110° | 168.05 | 240, 240 |
| Down | (90, 0, 0) | 下 (−Y) | **前 (+Z)** | 右 (+X) | 480×480 | 110°×110° | 168.05 | 240, 240 |

- 水平面的垂直视场 = 2·atan(0.75) = 73.74°，所以宽高比 4:3 时水平正好 90°。上下两面 fx = 240 / tan 55° = 168.05。
- **上下两面的画面上方都指向 rig 的前方**。向上那面因此是"仰面躺着、头朝前"看到的样子，画面右方是 rig 的左边；向下那面像看地图，右方就是右边。
- 内参的约定和 `vrc-vr` 的 `Fov::intrinsics` 一样：像素 i 覆盖 [i, i+1)，中心在 i + 0.5。
- 覆盖范围：水平面在面中心方向覆盖仰角 ±36.87°，在面的接缝（斜 45°）处 ±27.94°；上下两面在正前后左右方向覆盖 |仰角| ≥ 35.0°，在斜 45° 方向 ≥ 26.34°。处处有重叠（至少约 1.6°），**整个球面没有缝**。
- 角分辨率：水平面中心 8.38 px/°，边缘 16.76 px/°，水平平均 10.67 px/°；上下两面中心只有 2.93 px/°（只够看地面和天花板的大致样子）。

**像素 → rig 坐标系里的方向**（面内像素 (i, j)，左上原点）：

```
x = (i + 0.5 - cx) / fx        // 相机右为正
y = (cy - (j + 0.5)) / fy      // 相机上为正
水平面（朝向 φ = 0/90/180/270）：d = (x·cosφ + sinφ,  y,  −x·sinφ + cosφ)
Up：  d = (−x,  1,  y)
Down：d = ( x, −1,  y)
```

这是 `Quaternion.Euler(欧拉角) · (x, y, 1)` 展开的结果。再乘以 rig 的偏航 `R_y(rig_yaw)`（俯视顺时针）就是世界方向。

### 3.3 深度

**深度的定义**：z = 沿该面相机光轴的距离（米），不是射线长度。射线长度 = z·sqrt(1 + x² + y²)。

**来源（`Route`，条码里的 route 字段）**：

- **D1（默认）**：纯深度相机的深度图，反向 Z（D3D11/DXVK 上 `UNITY_REVERSED_Z` 有定义），HUD 用相机的 near n = 0.05、far f = 100 换算：
  `z = n·f / (n + raw·(f − n))`；raw = 0 是什么都没画到（天空、超过 far）。
- **D2**：编码四边形写进面的 alpha 的就是 z（半精度浮点，相对误差约 0.05%）；≥ 60000 表示什么都没画到。

**编码 E1C（带校验的 8 位对数深度）**，z 的对数范围 zmin = 0.25 m、zmax = 64 m（条码里的 range 字段）：

```
t = clamp(ln(z / zmin) / ln(zmax / zmin), 0, 1)
q = round(254·t)；什么都没有（天空、超过 far）：q = 255
R = q，G = 255 − q，B = tri(q) = |2q − 255|
```

- 这些都是 **sRGB 字节值**：着色器输出 `GammaToLinearSpaceExact(字节/255)`，眼睛画面是 sRGB 格式时存下来的正好是这个字节。
- 每级相对步长 ln(256)/254 = 2.17%，解码误差 ±1.09%（半级）；z < 0.25 m 记作 0，z ≥ 64 m 记作 254。什么都没有是 (255, 0, 255)。
- **为什么要三个通道**：VRChat 把自己的 UI（别人的名牌、相机的取景框）画在整只眼画面的最上面，盖住我们的 HUD，位置就是它们在正常视野里的位置。右眼被盖住的像素如果只看一个灰度，会被当成深度：名牌的深灰底（约 30, 30, 35）和白字都"是灰的"，会读成假的近处物体。E1C 的三个通道互相约束，灰色和常见的 UI 颜色都过不了下面的校验。
- 以前有过 8 位灰度（E1）和粗 + 细两通道（E2）两种编码，已删掉，只剩 E1C。

**解码和校验**（先用 3.5 的标定把每个通道**分别**换回编码值 R'、G'、B'）：

```
qR = R'，qG = 255 − G'
有效：|qR − qG| ≤ 4 且 |tri(qR) − B'| ≤ 6     （容差先这样，用真实画面再调）
无效 → 是 UI 覆盖，没有深度；遮掉，外扩 2 px
有效且 qR = 255 → 没有深度（天空）
有效且 qR = 0  → 也当未知（见下：纯青色正好是 q = 0）
其余 → z = zmin·(zmax/zmin)^(qR/254)
```

- 编辑器里的结果（5.1）：所有 256 级在每个通道各加 ±1 抖动后都能通过；下面这些 UI 颜色都过不了：名牌深灰底 (30, 30, 35)、浅一些的灰 (60, 60, 66)、白、黑、中灰 (128, 128, 128)、黄字 (255, 220, 0) 和 (255, 255, 0)、绿点 (0, 255, 0) 和 (60, 200, 80)、青圈 (0, 200, 255) 和 (64, 224, 255)。这些颜色和深度各占一半混合时，95.2% 能被认出来。
- 唯一碰撞：纯青 (0, 255, 255) 正好是 q = 0 的编码（≤ 0.25 m）。D1 的深度相机排除了 bot 自己的身体，0.25 m 以内几乎没有真实物体，所以 q = 0 一律当未知。VRChat 的青圈实际是什么颜色，要在真实画面里看。
- **左眼**没有校验，按右眼找：取右眼的无效遮罩，按 UI 的双目视差往左眼 UI 所在的一侧横向外扩（近处 UI 最坏约 fx·0.063/1.0 m ≈ 50 px，1920 px、100° 时），再加上左眼文字识别找到的名牌框（文字框向左延伸到图标）。遮掉的像素当未知：没有颜色也没有深度，下游只用有效的邻居或后面的帧补，不猜。
- 完整的约定（两端共用）在 `voice/pano-depth-check-spec.md`。

### 3.4 编码在后处理下

HUD 是在眼睛相机里画的，世界的后处理（PPv2）在它之后运行，至少会加 ±1 的抖动，可能还有色调映射、调色、泛光、暗角。所以 bridge **必须**每帧用标定格把字节换回编码值，不能直接当编码值用；调色和抖动对 R、G、B 的影响可能不一样，三个通道分别拟合。彩色面不受影响的部分：6 台相机本身没有后处理（avatar 相机上没有 PostProcessLayer），左眼的彩色只多了眼睛这一道后处理。

### 3.5 保留区（左下 960×480）

NDC（y 向上，−1..1）和像素（1920² 眼睛，左上原点）对照，像素 x = (ndc_x + 1)·960，y = (1 − ndc_y)·960：

| 内容 | NDC | 像素 x | 像素 y | 哪只眼 |
|---|---|---|---|---|
| PosBeacon（不动） | x −0.96..−0.74，y −0.96..−0.86 | 38.4..249.6 | 1785.6..1881.6 | 两眼 |
| HUD 不画的范围（PosBeacon 外扩一格） | x −0.97..−0.73，y −0.97..−0.85 | 28.8..259.2 | 1776..1891.2 | 两眼 |
| 元数据条码 0x5B（22×10 格，每格 0.01） | x −0.96..−0.74，y −0.84..−0.74 | 38.4..249.6 | 1670.4..1766.4 | 两眼 |
| 标定带，16 格，每格 0.025（24 px） | x −0.96..−0.56，y −0.69..−0.665 | 38.4..422.4 | 1598.4..1622.4 | 右眼 |
| 暗角标定对 1（64 \| 192） | x −0.66..−0.61，y −0.96..−0.935 | 326.4..374.4 | 1857.6..1881.6 | 右眼 |
| 暗角标定对 2 | x −0.36..−0.31，y −0.96..−0.935 | 614.4..662.4 | 1857.6..1881.6 | 右眼 |
| 暗角标定对 3 | x −0.36..−0.31，y −0.60..−0.575 | 614.4..662.4 | 1512..1536 | 右眼 |
| 暗角标定对 4 | x −0.10..−0.05，y −0.60..−0.575 | 864..912 | 1512..1536 | 右眼 |
| 其余 | | | | 黑 |

- 标定带第 k 格（k = 0..15，从左到右）是深度级 q = 17k（0、17、…、255），和深度一样按 E1C 写成 (q, 255 − q, |2q − 255|)。
- 暗角标定对：每对两格，左格 q = 64、右格 q = 192，同样按 E1C 写。四对离画面中心的距离（NDC 半径）约 1.14、1.01、0.68、0.59；标定带本身横跨 0.89–1.19。
- PPv2 的暗角是按半径乘一个系数，且在调色之前，所以模型是：观察值 = F(g(r)·L(编码值))，L 是编码值对应的线性亮度。bridge 用标定带和四对一起，对 R、G、B 各拟合一条单调的 F，共用一个 g(r)（用 r² 的多项式即可）。没有后处理的世界，F 是恒等、g = 1。
- 标定格只放在保留区里，没有放在眼睛四角：四角都被面占着。四对的半径从 0.59 到 1.14，已经覆盖了面区域的大部分半径范围（面区域最远的角是 1.41，那里只能外推）。
- 左眼保留区里，标定格的位置是黑的。

### 3.6 元数据条码（magic 0x5B）

位置见 3.5，格式和 PosBeacon 完全相同：22 列 × 10 行，第 0 行白黑交替，第 9 行、第 0 列、第 21 列全白，第 1–8 行、第 1–20 列是 160 位数据（按行从左到右），白为 1、黑为 0。两只眼画的是同一个条码。

| 位 | 字段 | 说明 |
|---|---|---|
| 0–7 | magic | 0x5B |
| 8–39 | x | `PanoEye`（相机中心）的世界坐标，float32 原始位 |
| 40–71 | y | 同上 |
| 72–103 | z | 同上 |
| 104–119 | rig_yaw | rig 的 +Z 在世界里的朝向，从世界 +Z 顺时针（俯视），`round(yaw/360×65536) mod 65536`，和 PosBeacon 的 yaw 同一约定 |
| 120–127 | seq | `floor(_Time.y×30) mod 256`，和同一帧 PosBeacon 的 seq 是同一个时钟 |
| 128–131 | age | `min(15, floor(_PanoAge×30))`，`_PanoAge` 是 `Pano` 打开后的秒数（动画驱动），单位 1/30 s，到 15 封顶 |
| 132–135 | layout | 布局编号。1 = 本文 3.1、3.2 的 6 面布局；0 保留（无效） |
| 136–137 | route | 深度来源：0 无，1 D1，2 D2 |
| 138–139 | code | 深度编码，**只有 2（E1C）有效**；0、1、3 无效，读到就丢掉这一帧 |
| 140–141 | zmin | 对数范围下限 = 2^(zmin − 4) m（2 → 0.25 m） |
| 142–143 | zmax | 对数范围上限 = 2^(zmax + 5) m（1 → 64 m） |
| 144–159 | crc | CRC-16/CCITT-FALSE（多项式 0x1021，初值 0xFFFF，不反转，不异或），按位计算，覆盖第 0–143 位 |

每个字段高位在前。第 120–143 位在着色器里是一个 24 位字：`(seq << 16) | (age << 12) | (layout << 8) | (route << 6) | (code << 4) | (zmin << 2) | zmax`。

## 4. 读码端（bridge）

1. 打开：OSC 发 `/avatar/parameters/Pano` = 1。
2. 每次拿到两只眼的画面：
   1. 两只眼照常读 PosBeacon（左下角，位置不变）。
   2. 两只眼读条码 0x5B（3.5 的位置，取每格中心 3×3 像素平均，按第 0 行定阈值，同 PosBeacon 文档第 4 节）。要求：magic 0x5B、CRC 对、layout 是认识的编号（现在是 1）、code = 2、两只眼的 160 位相同、seq 和同一帧 PosBeacon 的 seq 相同、**age ≥ 2**（打开后 ≥ 67 ms；之前的帧可能是上次关掉时残留的旧面）。有一条不满足就丢掉这一帧，不猜。
3. 左眼：按 3.1 切出 6 块。每块是一个透视视图，内参见 3.2，旋转 = `R_y(rig_yaw) · R_face`。
   - 相对头的方位：先按 3.2 的公式得到 rig 坐标系里的方向 d，方位 = atan2(d.x, d.z)（向右为正），仰角 = atan2(d.y, sqrt(d.x² + d.z²))。相对航向 = rig_yaw + 方位 − head_yaw，换到 (−180°, 180°]。head_yaw 取同一帧 PosBeacon 两眼 yaw 的圆周平均。水平面的中心方向就是 rig_yaw + 面朝向 − head_yaw、仰角 0。
   - 拼成 equirect：每个输出像素取"把这个方向看得最居中"的那个面，和 `vrc-scene` 的 `Panorama::stitch` 同一规则；输出以航向居中、向右为正，和 `vrc-nav` 的 `marked_panorama` 一致。
4. 右眼：
   1. 读标定带和四对暗角格，每个通道拟合 F，再拟合 g(r)（3.5）。残差大于 3 级时，这一帧的深度只当"远近顺序"用。
   2. 逐像素：字节 → 反标定 → 编码值 → 按 3.3 校验，无效的（UI 覆盖）遮掉并外扩 2 px → 有效的解码成 z（米）。左眼按 3.3 的办法遮 UI。遮掉保留区；边缘处做 3×3 中值，丢掉深度梯度大的像素（泛光、抗锯齿会糊开边缘）。
   3. 反投影：面内像素 (i, j) 和 z → 相机坐标 z·(x, y, 1) → rig 坐标 `R_face·` → 世界坐标 `p = 条码位置 + R_y(rig_yaw)·R_face·z·(x, y, 1)`（Unity 世界）。换到地图坐标：`x_map = x`、`y_map = y`、`z_map = −z`（同 PosBeacon 文档第 3 节）。
5. 拿到需要的 1–2 帧后，OSC 发 `Pano` = 0 关掉。
6. 打开期间的眼睛画面不送进普通的双目匹配、文字识别和视觉模型（整只眼都是全景）。名牌识别改在面图上做（如果名牌拍得到，见 5.2）。

1. **rig_yaw 不跟身体也不跟头**：原地转 90°（PosBeacon 的头 yaw 141° → 231°），rig_yaw 一直是 140.26°。原因：第一版的 rig 继承化身根的旋转，而 VR 里化身根跟的是游玩空间。改为 `VRC Rotation Constraint` 只取 Head 的偏航（2.1 第 2 步）。
2. **相机中心离眼睛 7–12 cm**：转身后条码位置 (5.469, 1.175, 0.97)，两眼平均 (5.369, 1.176, 0.99)；蹲下 0.2 m 时条码 y 1.039，眼睛 0.97。原因：第一版把视点偏移放在 rig 的坐标系里，rig 又跟着 Head 骨骼原点走，头一转、一低，偏移就不对了。改为 Head 下带 Head Chop 的锚点，rig 零偏移跟它（2.1 第 1、2 步，7.2）。

## 6. 注意

- **代价**：6 台彩色相机，D1 再加 6 台纯深度相机，**每帧一共 12 台相机**。每台都要做一遍完整的剔除、前向绘制和方向光阴影（内置管线不能按相机关阴影），CPU 渲染线程的开销大约是主眼渲染的 8–12 倍（纯估算，未实测）；D2 是 6 台相机，但每台多一遍深度预渲染，眼睛相机也多一遍。GPU 侧 6 个面共约 3.2 Mpx（D1 再加同样大小的纯深度），比两只眼的 7.4 Mpx 少。所以**平时一定关着**，用时打开、拿到 1–2 帧有效画面就关。
- far 设成 100 m，限制阴影距离和可见物体；HDR、MSAA 都关。
- 打开期间 bot 的两只眼都被全景占满，看不到正常画面；普通的视觉管线要暂停。
- 打开后头 2 帧（age < 2）的面可能是上次关掉时留下的旧图，必须丢掉。
- rig 的偏航取头的偏航，头几乎正上或正下看时偏航不稳定，面会跟着乱转。这时的帧要靠条码里的 rig_yaw 换算，或者等头回到正常角度再拿。
- 上下两面分辨率低（中心 2.93 px/°），看地面和天花板的大致样子够用，认东西要靠水平面。
- 深度里只有不透明物体：玻璃、水面、粒子、名牌、UI 都不在深度里（D1 的深度相机和 D2 的 `_CameraDepthTexture` 都是这样）。bot 会"看穿"玻璃，撞玻璃的标记逻辑要保留。
- 世界的后处理会改变右眼的字节，必须每帧用标定格按通道反变换（3.4、3.5）。
- VRChat 的 UI（名牌、相机取景框）画在全景上面，两只眼都会被盖住：右眼靠 E1C 校验找出来，左眼按 3.3 的办法遮掉。彩色和条码不受影响（条码是黑白块，PosBeacon 已经证明扛得住）。
- 化身性能等级：D2 的深度灯会让化身落到 Poor（灯这一项，关着的灯也算）；相机和 RenderTexture 不计入等级（RenderTexture 是否计入贴图内存没有官方说法）。D1 没有新加的灯。
- 化身上传期间不要做测试烘焙或进 Play 模式（7.3）。`RunTests` 不烘焙，可以放心用，但也不要在上传进行中跑。

## 7. 实现时踩过的坑

### 7.1 `LoadPrefabContents` 的场景渲染不出来

- 现象：第一次跑测试，左眼右眼读回来全是测试相机的清屏色；连一个普通的方块都渲染不出来。
- 原因：`LoadPrefabContents` 把预制体放在一个内部的预览场景里，`Camera.scene` 指过去、相机类型换成 Preview 都没用。`EditorSceneManager.NewPreviewScene()` 新建的预览场景则正常。
- 解决：结构和动画器的检查照样在 `LoadPrefabContents` 上做；渲染另建预览场景，用 `PrefabUtility.InstantiatePrefab(资产, 场景)` 放一个实例进去，改名，测完 `ClosePreviewScene`。不碰当前打开的场景，也不触发 NDMF。
- 顺带：测试相机的清屏色要选一个既不是天空 (255, 0, 255)、也不是任何深度级的颜色，否则"没画"会被当成合法的深度，检查会假通过。现在用黄色 (255, 255, 0)，它过不了 E1C 校验。

### 7.2 rig 跟化身根：VR 里既不跟头也不跟身体，相机中心也偏

- 第一版：rig 挂在化身根下，`VRC Position Constraint` 零偏移跟 Head 骨骼原点，视点偏移放在子物体 `PanoEye` 上（固定在 rig 坐标系里），旋转继承化身根。当时这样做，是因为 VRC 约束的偏移在哪个空间里算、会不会被第一人称的 Head 缩放缩没，文档都没写，想绕开。
- 现象（5.3）：原地转 90°，rig_yaw 不动；相机中心离眼睛 7–12 cm，蹲下时差得更多。
- 原因：
  - VR 里化身根跟的是游玩空间，不是身体，更不是头，所以继承根的旋转等于偏航不动。
  - 视点偏移在 rig 坐标系里，rig 的朝向不对，偏移的方向也就不对；低头、蹲下时 Head 骨骼原点和眼睛的相对位置也变了。
- 解决：
  - 位置：Head 下放锚点 `PanoAnchor`（在视点），加 `VRC Head Chop`（缩放 1、Always Apply），rig 零偏移跟它。锚点跟着头转、跟着头低，就在眼睛处。
  - 朝向：`VRC Rotation Constraint` 源是 Head、只影响 Y，偏移取 Head 静止姿态的逆。编辑器里用 VRChat 的约束管理器实际求解验证过（5.1"位姿"）。
  - 条码里的位置和 rig_yaw 仍然取 `PanoEye` 的真实位姿，bridge 不用改。
- 剩下的风险：第一人称下 Head 被缩到接近 0，Head Chop 能不能保住锚点的**位置**（不只是缩放），VRChat 文档没说清，编辑器里也模拟不了。PosBeacon 用的是同一个办法，但它的读数是相机位置，证明不了这一点。保不住的话锚点会塌到 Head 骨骼原点（这个化身上比视点低约 5 cm、靠后约 8 cm），5.2 第 2 步一测就知道。万一保不住，备选是把锚点放到 Head Chop 已知能保住的骨骼上，或者改用 `VRC Parent Constraint` 的源偏移，都要再实测。

### 7.3 测试烘焙不能和上传同时做

和 PosBeacon 文档 7.3 相同：NDMF 把生成的资源写到 `__Generated/<化身物体名>/`，上传期间做测试烘焙会把构建刚生成的资源换掉。这里的测试完全不烘焙；测试用的实例也改了名，不和化身同名。

### 7.4 D2 的层问题（未解决，只能实测）

- D2 的编码四边形必须被 rig 的相机拍到才能把深度写进 alpha。但 VRChat 运行时会改写化身物体的层：本地化身的渲染器大概率在 PlayerLocal(10)（和它在镜子里的克隆在 MirrorReflection(18)）。相机排除了这两层，四边形就不会运行，alpha 是垃圾。
- 现在的设置是"最有机会"的那种：D2 时相机额外勾上 PlayerLocal（`D2PlayerLocal`）。代价：
  - 面里会出现 bot 自己的无头身体，主要在向下那面；bridge 要用"深度 < 0.6 m"和面的位置遮掉。
  - **PosBeacon 也会出现在每个面的左下角**（它只按距离判断，不区分立体相机，离视点 15 cm，在 0.35 m 以内）。这些假方块按面缩小后画进各块，PosBeacon 自己的那块（保留区左下）不受影响，但不要在块里找角标。不改 PosBeacon。
  - 不勾 MirrorReflection：克隆有头，相机在头里会拍到头的内面。
- 深度灯没开或没生效时（参数没到、画质里阴影关了），相机读到的是别的相机留下的深度，alpha 也是垃圾。灯和相机放在同一个动画状态里一起开关；bridge 再做合理性检查（天空的颜色处应该是"没有深度"）。
- 编辑器里层不会被改写，所以 D2 在编辑器里能通过，不代表 VRChat 里能用。先用 D1。

### 7.5 纯深度 RenderTexture 怎么读

- `UNITY_DECLARE_DEPTH_TEXTURE` 在 SPI 变体下展开成纹理数组，在非立体变体下是 `sampler2D_float`，两者都不适合读一张普通的纯深度图：前者取错层，后者没有 `Load`。HUD 用普通的 `Texture2D` 声明，`Load` 按整数像素读，SPI 和非立体都对。
- 编码四边形读的是相机自己的 `_CameraDepthTexture`，只在非立体变体里声明它，用 `tex2Dlod` 在像素中心取值。
- 纯深度图的 Shadow Sampling Mode 设为 None（IkeHUD 的设置），否则可能被当成阴影贴图做比较采样。
- D32_SFloat 在 VRChat 里还没用过；IkeHUD 用的是 D16_UNorm，能用。D16 在反向 Z、near 0.05 时，64 m 处每级约 1.25 m（约 2%），和编码的一级差不多。VRChat 里 D32 不行就换 `DepthFormat = D16_UNorm`。
