# 谁在说话：声音方向 + 名牌（2026-10-08）

> bridge 一侧的说话人归属：从游戏的双耳输出估计声音从哪个方向来，再看哪个玩家的名牌在那个方向、名牌外圈的说话光环有没有亮，把一段话归到一个玩家身上。还没有声纹。名牌来自两处：bot 的眼睛（OCR + 双目）和用户相机的镜头（绕着 bot 转的远程眼睛，只有方位，第 2.4 节）。和插件、AstrBot、Codex、infra 之间的约定见 `P:\Astrbot\voice\speaker-contract.md`（本文只管第 1 节，bridge → 插件）。决策见 [decisions.md](decisions.md) 的 D32、D35。

## 1. 链路

```text
vrc_out.monitor (float32 双声道 48 kHz)
   │  parec --channels=2 --channel-map=front-left,front-right
   ▼
采集任务（tokio，每 20 ms 一块）
   ├─ 单声道混音（按主导时延对齐两耳再相加，对齐方式由分析线程定）──> /v1/stream 二进制帧（不变：s16le 单声道 48 kHz，960 样本）
   └─ 这一块 + 它在客户端时钟上的位置（是否计入）+ 读到它的时刻 ──> 有界队列（50 块，1 s）
          ▼
分析线程 vrc-audio::Front（每 10 ms 一帧）
   ├─ 语音检测 → 分段（客户端样本时钟）
   └─ 每个时频点对 HRTF 模板投票（以头为参照的方位）
          │  按当时头的朝向转到固定坐标系（追踪空间的偏航）
          ▼
speaker.rs：每段的投票 + 候选玩家（名牌方位、名牌光环）+ "不认识" ──> speaker 事件（同一个队列）
   ▲
   ├─ 视觉线程（自己的 EyeTap）：OCR 读名牌，在全景深度里定位，量名牌外圈的光环；跟随和环视读到的名牌也送进来
   └─ 用户相机的镜头（orbit.rs，桌面窗口的画面）：OCR 读到的名牌 → 相对头的方位 + 光环
```

- **客户端样本时钟**：从客户端连上时的 0 开始，只数真正放进队列的音频样本；队列满被丢掉的帧不算。所以插件从连上起收到的样本数就是 bridge 的计数，线上不需要序号。
- **分析在自己的线程上**，不占 tokio 的工作线程：采集任务只做混音、把块放进队列，再把块连同它的时钟位置和读到的时刻交给分析线程。分析按块自带的时钟和时刻算，所以排队的延迟不影响时间和样本位置。分析跟不上、队列满了时，新块不分析（客户端照样收到音频，时钟照样走），日志里每 10 s 最多警告一次。本机（Windows，release）用 Steam 表分析一块约 100 µs（改之前约 400 µs：似然的模板按频点转置、σ 折进系数、只对最近的方向附近求指数；GCC-PHAT 的相位因子预先算好）；`cargo test --release -p vrc-audio -- --ignored --nocapture timing` 可以复测。
- **`speaker` 事件**和音频帧走同一个队列，在它说到的音频之后（分析比混音晚一点）。一段话进行中每 ~250 ms（按音频时间，25 帧）发一次 `final:false`，`end` 随之增长；结束时再发一次 `final:true`。同一个 `start` 后发的替换先发的。

```json
{"type": "speaker", "start": 123456, "end": 140000, "final": false,
 "name": "xkeyC", "user_id": "usr_...", "bearing_deg": -32.5, "confidence": 0.82,
 "cues": {"doa": 0.9, "glow": 0.7, "glow_onset": true, "evidence": "glow"},
 "candidates": [{"name": "xkeyC", "p": 0.82}, {"name": null, "p": 0.12}]}
```

- `name`、`user_id` 认不出来时为 null；`bearing_deg` 相对 bot 的头，向右为正。
- `cues.doa`：这段话的投票在该玩家方位附近（±8°，或前后镜像那边的 0.8 倍，取大的，第 2.5 节）占的量，除以全圈最多的那一处（1 = 就是峰）；`cues.glow`：这段话期间（开始前 0.1 s 到结束）看到该名牌光环亮的比例，上一段话留下的 0.9 s 尾巴不算；`cues.glow_onset`：光环是不是正好在这段话开始时亮起（第 2.5 节）。没看到名牌时两项都是 null。
- `cues.evidence`：靠什么归属的（第 2.5 节）：`glow`（bot 眼睛看到名牌亮）、`lens`（只有用户相机的镜头看到名牌亮）、`direction`（只有声音的方向，名牌没看到亮：概率封顶 `--doa-only-cap`）、`none`（票也不够，只剩多久前定位的先验，同样封顶）。没归属时说的是有没有方向。
- `candidates`：融合的后验（第 2.5 节），最多 3 项、每项 ≥ 0.1，从大到小；`name` 为 null 的一项是"不认识的人"。infra 按它给转写加 `xkeyC: …`、`[xkeyC 62% / someone 30%]: …` 或 `[unknown speaker]: …` 的前缀（`speaker-contract.md` 第 3 节）。`name`、`confidence` 照旧（最高的候选，归属规则不变）。
- 有声帧过半落在 bot 自己说话期间（以及之后 `--echo-tail-ms`，默认 0.4 s）的语音段：`name` 为 null，`cues` 为 `{"bot_echo": true}`，`candidates` 为 `[{"name": null, "p": 1.0}]`（第 2.6 节）。
- 语音太少被丢掉的段，如果已经发过 `final:false`，补一个 `final:true`、`name` 为 null、`cues` 为 `{"dropped": true}`、`candidates` 同上。

## 2. 方法

### 2.1 方向（`crates/vrc-audio`）

- VRChat 的声音由 Steam Audio 用默认 HRTF 做双耳渲染，没有反射和遮挡：等于一个没有噪声、HRTF 已知的假人头。所以用**模板匹配**：
  - STFT：960 点 Hann 窗（20 ms），每 480 点（10 ms）一帧。
  - 只用 200–6000 Hz 的频点，并且要两耳在这个频点上相干（最近几帧平滑的互谱相干度 ≥ 0.85：只有一个声源主导这个点），高出该频点自己的噪声底 6 dB。
  - 每个保留的时频点，用观测到的两耳相位差和电平差，对每个模板方向算似然（σ 相位 0.6 rad、电平 3 dB），在方向上归一化后算一票。一段话的所有票加起来是一张全圈直方图：一个人一个峰；同时说话的两个人两个峰（DUET 式）。
  - 前后有镜像：同一个侧向角（`a` 和 `180 − a`）的两耳差几乎一样。直方图保留整圈，由候选玩家和转头去分。
- **模板**两种，接口相同（`vrc_audio::Hrtf`）：
  - `assets/hrtf/steam-default-48k.bin`：用官方 Steam Audio SDK 4.8.1 的 `phonon` 渲染的默认 HRTF（见第 5 节）。默认用它。
  - 球形头模型（Woodworth 时差 + 随频率增长的头影电平差）：没有表时用。它前后完全对称，分不了前后。
- **按头的朝向累计**：每帧的投票（以头为参照）按那一刻头的偏航转到固定坐标系再累加。头在一段话里转了，真实方向的票还是叠在一起，镜像的票则被拉开（顺带利用了"转头分前后"）。头的朝向取动画线程实际发给头显的位姿（含动画的晃动和张望），减去音频延迟 `--audio-latency-ms`（默认 60 ms，待测）。
- **合成信号上的结果**（单元测试）：单个说话人，峰在 ±3° 内（球形头和 Steam 表都是）；用 Steam 表时真实一侧的票是镜像一侧的 1.7–6 倍；两个人（-40°、35°）各一个峰；两耳加独立噪声峰不动。

### 2.2 给客户端的单声道

- 两耳直接相加会给侧面的声音挖出梳状缺口（侧面时差约 0.65 ms，缺口在约 770 Hz 及其奇数倍），伤 ASR 和声纹。
- 做法：用平滑后的互谱算 GCC-PHAT 时差（可信度 ≥ 0.4 才用，取最近 5 次的中位数，变化不到 1 个样本不改），把超前的那只耳朵延迟这么多再相加。超过 1 s 的有声帧都没有可信时差（多人、弥散声），改用响的那只耳朵（另一只要响 3 dB 才换）。没声音时保持原样。
- 每次改变都在一块（20 ms）内余弦交叉淡化，不出咔哒声。

### 2.3 名牌和光环（`crates/vrc-bridge/src/speaker.rs`）

- **候选**：房间里（VRChat 日志的玩家名单）最近被定位过的玩家。名牌的三维位置来自 OCR 加全景深度（和跟随同一套 `panolook`，D42 起只有全景）；跟随每次取景、环视和 `goto` 走完后的环视读到的名牌都送进来。用户相机的镜头读到的名牌只有方位（第 2.4 节）：放在那个方向 2.5 m 处，只用它的方位，不投影到眼睛的画面里；深度定位过的名牌，方位和镜头读到的相差 20° 以内就保留深度的位置（算作刚刚看到）。超过 60 s 没再看到、或 bot 之后走了 2 m 以上（行走时追踪空间整体平移，旧位置作废）的不算候选。方位按名牌位置和现在头的位置算（固定坐标系）。`GET /v1/speakers` 的玩家里 `placed_by` 是 `depth` 或 `bearing`。
- **视觉线程**有自己的 EyeTap（不占头显锁）：
  - 有人在说话（或刚说完 1 s 内、或在录制）：每 250 ms 取一帧，OCR 最多每 1 s 一次，跟随刚读过名牌（600 ms 内）就不重复读；不 OCR 的帧，把 2 s 内定位过的名牌按三维位置投影到这一帧再量。
  - 只读全景帧（D42）：眼睛上的名牌和镜头 1 s 内读到的名牌，在全景深度里定位；普通视角（租给菜单时）没有深度，不读。
  - 没人说话：房间里有别人时每 10 s 取一帧（读一次名牌、更新各名牌的"安静样子"）。
  - 抓帧是按需的（D29）：只有有人在说话、或者没有别人（跟随）在让 Monado 抓帧时，才去碰 `.want`；跟随正在抓帧时，安静时的那一帧直接读现成的，不再续期。
- **光环长什么样**（2026-10-08 实测：朋友的名牌，2–3 m，30 fps 录 60 s，两段说话）：
  - 说话时名牌胶囊外面紧贴着一圈**细的描边**（约 3 px，1920 宽的眼睛里），颜色是名牌的主题色：好友是金色（和名字同色，约 RGB 242,190,50），非好友是亮青色；VRC+ 可能不同。
  - 胶囊左右两侧有淡淡的**波纹弧**，随音量起伏。
  - 描边比采集到的声音**早约 0.1 s** 亮起，停顿不到约 1 s 时一直亮着，话说完后**约 0.9 s** 才灭；亮度基本不变（只有亮和灭）。
  - 不亮时胶囊边缘就是深色的胶囊底（约 RGB 30,30,35；实测 22,21,28）贴着背景。
- **测量**（`glow_stats`，对任何画面：眼睛的帧或者 RGB 图，所以用户相机的画面也能用）：
  - 胶囊的模型按名字文字框的高 h 算：从文字左边 3.0 h（左端有头像）到文字右边 0.85 h，高 3.0 h，两端是半圆；沿外沿取 48 个采样点。
  - 胶囊底的颜色取文字框里的暗像素的中位数，容差按它们的离散度（4–12 级）。每个采样点沿法线从模型里面 0.5 h 走到外面 0.5 h，连续两个以上胶囊底像素之后的第一个非胶囊底像素就是边缘（OCR 框松一点紧一点都能找到）；边缘外 0.12 h（2–6 px）的带子里取最饱和的像素。背景和胶囊底一样暗时找不到边缘，算没亮。
  - **光环比例**：采样点里"强饱和"（色度 max−min ≥ 0.30、亮度 ≥ 0.45）且色相和其中最多的那种相差 30° 以内的比例。和颜色无关：金色、青色都一样。
  - **波纹**：两端（法线接近水平）的带子外再往外 0.8 h，同一色相的强饱和像素的比例。
  - **分数** = 光环比例 + 0.5 × 带子的平均色度 + 0.25 × 波纹。实测录像：不亮 0.19–0.32（中位 0.22），亮 1.08–1.41；只有大片饱和背景贴着胶囊时不亮的分数才高（紫墙那一侧约 0.1）。
- **判定**（每个名牌一份 `Plate`）：
  - 和它自己的"安静样子"比，眼睛和镜头**各有一份**安静样子（画面不同）。安静样子立刻跟着降，慢慢（20 s）跟着升；名牌亮着时、bot 的声音可能被回放时都不更新。还没有安静样子时按 0.2 算。连续亮 30 s 以上当成画面变了（饱和的背景），安静样子照样跟着升。
  - 光环本身只有亮灭，所以**一帧就算亮**：高出安静样子超过 `--glow-on`（0.30）算亮，低于 `--glow-off`（0.15）算灭，中间保持。光环自己会跨过 1 s 以内的停顿，所以不再加包络。
  - 每次看到都记下（时刻、亮否、是否回声期），保留 60 s；镜头的 OCR 结果晚到时按时刻插进去。

### 2.4 用户相机的镜头：一圈的名牌（`crates/vrc-bridge/src/orbit.rs`）

化身上的相机拍不到名牌，全景开着时眼睛的画面是全景拼块（拼块里没有名牌；VRChat 的名牌 UI 仍画在上面，在普通视图里的位置：只有前方的那些，`panolook` 读它们）：用户相机的直播画面（桌面窗口）是名牌的来源（[agent-vr-use.md](agent-vr-use.md) 第 8 节、D35）。眼睛那条路照旧，两者并行。

- bot 站着时镜头绕头转（默认半径 0.7 m、3 s 一圈、向外看、向下 8°）；走路时镜头在头的后上方朝前进方向看；**有人开口时镜头转向他**（见下）。这几种时候都读名牌。
- 桌面窗口用 ffmpeg x11grab 连续抓（`grab_fps`，默认 10 帧/秒，原始 RGB 走管道，只保留最新一帧）。每帧按到达时刻减去 `lag_ms`（默认 70 ms：游戏 1–3 帧后才用上新的 Pose）找当时镜头的位姿：绕圈时在前后两个 Pose 之间插值，走路时就是那个停着的 Pose；中间夹着别的放置（拍照、扫一圈）的帧不用。
- 每秒 `ocr_hz`（默认 4）次、有人说话时 `ocr_hz_hot`（默认 5）次、镜头转向说话的人时 `attend.ocr_hz`（默认 5）次，把最新一帧送 infra OCR（`vrc_players::OcrClient`），名字和房间名单匹配（`vrc_players::names`）。
- **方位**：文字框中心的像素 → 镜头的射线（视场按 `/usercamera/Zoom` 当竖直视场；不对的话在 `fov_deg` 里设；都没有用 60°）；镜头离头有偏移（绕圈 0.7 m、走路时在后上方），所以取射线上离头 2.5 m 的点，算它相对头的方位（世界的偏航），再用位置角标和头显位姿的偏航差换到追踪空间。距离不知道，只用方位。
- **光环**：同一帧上按 OCR 的文字框量（第 2.3 节的 `glow_stats`），算镜头那份安静样子。镜头一圈里每个名牌只有一部分时间在画面里，所以镜头的光环是稀疏的；靠起亮时刻对齐（第 2.5 节）用上。
- **有人开口：镜头转过去看**（`attend_onset`，**2026-10-09 起默认关**：每段话一开口镜头就甩过去太突兀；全景的眼睛画面上 VRChat 照样画出前方的名牌，bot 闲着被叫到时自己转过去，第 2.7 节。代码留着，设置里打开就恢复；[agent-vr-use.md](agent-vr-use.md) 第 8 节）。打开时：说话人追踪给出这段话的方位（`Speakers::voice`：已归属就用那个玩家的方位，否则用投票的峰，20 个有效频点就够；峰和镜像差不多时先看有候选的那边，另一边留作镜像），镜头放到头外 0.3 m 沿那个方位看。镜头不动，所以两次 OCR 之间的每一帧都在上次读到的文字框上再量一次光环（`saw_glow`，`glow.jsonl` 里来源是 `lens`）：光环的起亮时刻精确到一帧（10 帧/秒），起亮对齐（第 2.5 节）主要靠它。0.4 s 内那边没有名牌亮，就转去看镜像。看到这段话结束后 1 s。
- 读到的名牌送给说话人追踪（`saw_bearing`），也存下来（60 s）：`GET /v1/vr/usercam/names?since_ms=10000`，以后跟随和环视移植到全景时从这里读。

### 2.5 融合（每段话）

- 每个候选的权重 = 先验 × 方向 × 光环：
  - 先验：按多久前定位的，`exp(-age/30 s)`，最少 0.1。
  - 方向：这段话在该方位 ±8° 内的票，比随机落在那里多几倍（限制在 0.05–20）。这段话有效频点少于 60 个时不用方向。**前后折叠**：前后两耳差几乎一样（实测正前方的声音常常峰在正后方），所以也看该方位关于两耳连线的镜像（按这段话开始时头的朝向）那边的票，乘 0.8（`MIRROR_WEIGHT`：转头时真实一侧的票叠得住，略占优），两者取大。
  - 光环：因为话说完后光环还要亮 0.9 s，只看"这段话期间亮没亮"会把上一个人的尾巴算到下一段上，所以**按起亮时刻对齐**：
    - 光环起亮（前一次看到是灭的、1.2 s 以内的下一次看到是亮的，起亮时刻取两次中间）落在这段话开始前 0.1 s 的 ±0.3 s 以内（再加上两次看到间隔的一半，最多再加 0.3 s）：9；
    - 否则，这段话期间（开始前 0.1 s 到结束）看到亮的比例，不算已经灭掉的那段亮光的最后 `--glow-release-ms`（0.9 s，那是上一段话的尾巴）：`1 + 6 × 比例`；
    - 看到了但一直没亮（或只看到尾巴）：0.35；没看到：1。
- "不认识"也是一个选项：权重 0.25，房间里每有一个没被定位的玩家加 0.15（可能是背后看不到的人）。
- **只有方向时封顶**（2026-10-09，用户要求）：名牌没看到亮（没看到，或看到了一直没亮）的候选，只有声音方向和"附近有谁"（看过的名牌、镜头读到的方位、闲时一圈的扫视缓存，都经 `saw` / `saw_bearing` 进来）在支持他，归一化后的概率最多 `--doa-only-cap`（默认 0.55），多出来的给"不认识"。这样模型看到的是 `[xkeyC 55% / someone 45%]: …`，而不是笃定的 `xkeyC: …`。名牌亮了（眼睛或镜头看到，起亮对齐或期间亮）的候选不封顶：方向 + 光环一起就是笃定的。`cues.evidence` 说是哪种。
- 归一化后，最高的候选要比"不认识"高、并且 ≥ 0.4 才归给他；否则 `name` 为 null，`bearing_deg` 用投票的峰。封顶 0.55 时只有方向的候选通常还是归给他（0.55 > 0.45），只是 `candidates` 里看得出不确定；`--doa-only-cap` 设到 0.5 及以下就不再只凭方向归属。
- `candidates`：所有候选和"不认识"按后验从大到小，取 ≥ 0.1 的前 3 项。

### 2.6 bot 自己的声音

- bot 自己的语音不经过游戏输出，但别的玩家开着外放时会把 bot 的话回放回来，而且他们的名牌会亮，容易把 bot 的话算到他们头上。
- 回声期：bot 的语音播放期间（`Bridge::play` 排进去的音频播完为止，已含播放延迟）和之后 `--echo-tail-ms`（默认 400 ms：别人的网络和设备）。按帧算，不按段算：
  - 回声期里的帧不投票（不进这一段的方向直方图，也不进 attend 再听时的票）；
  - 回声期里看到的名牌，不更新它的安静样子，也不算进这段话"亮的比例"；
  - 一段话的有声帧**过半**在回声期里，整段才不归属（`bot_echo`），`/v1/vr/attend` 也不转向它。所以 bot 刚说完 0.2–0.8 s 就有人接话，这段话仍然照常归属，只是开头那点不投票。
- `GET /v1/speakers` 的每段有 `voiced_hops`、`echo_hops`。

### 2.7 转向说话的人（`POST /v1/vr/attend`）

0. **只在闲着时转**（2026-10-09，用户要求）：插件在被叫到时（唤醒词，或要回复的转写，`on_wake`）调它。bot 在跟随（包括跟随被模型的动作暂停着）、在动（里程计 1 s 内动过：走路、被推、掉落）、或 VR 菜单借着普通视图时，什么都不做，回 `{"ok": false, "reason": "busy", "busy": "following" | "moving" | "menu"}`（`speaker::attend_busy`，有单元测试）。插件不用改：它只记日志。闲着时 bot 自己转过去（先头后身，和下面一样平缓），之后全景眼睛画面上 VRChat 画的前方名牌就写着他的名字、亮着光环。
1. **选目标**（只看票够、不是 bot 回声的段）：
   - 带 `name`（转写里的说话人，即 bridge 自己先前的归属，经 infra 和 AstrBot 传回来）：这个人最近的一段（正在进行的，或 `since_ms` 内结束的）；
   - 没有 `name`、或没找到他的段：带了 `since_ms`（转写触发：转写在话说完之后才到，这时正在说的可能已经是别人）先选 `since_ms` 内结束的最近一段，没有才选正在进行的；没带 `since_ms`（唤醒词触发：唤醒词是在说话过程中听到的）先选正在进行的，没有才选 2 s 内结束的最近一段。
   - 回复里的 `picked` 说选的是哪种：`named`、`ended`、`running`。
   - 已归属给某个候选：转向他**现在**的方位；否则，前后折叠后和投票的峰在同一侧（±35°，`SIDE_MATCH_DEG`）的已定位的人（看过的名牌、镜头、闲时扫视的缓存），转写说的那个人优先（`from: "candidate side"`，名字带上），其次最近的；都没有才转向投票的峰，峰和它的前后镜像票数差不多（镜像 > 峰的 60%）时，哪边有候选就选哪边。
2. **暂停跟随**：和模型自己的动作一样接管跟随（`take_over`），`pause_s`（默认 8）后交还（`idle_later_for`）。现在跟随时不转（第 0 步），这一步只剩记账。
3. **转身**：目标离身体朝向 35° 以内只转头，否则整个人转（`turn_gently`，然后手回到身侧）；用时 `0.35 + 角度/160°` 秒，最多 1.6 s，缓入缓出。
4. **再听一次**：等 250 ms，再收最多 1.5 s 的语音（只用头已经转到位、偏差 4° 以内的帧）：
   - 正后方的票明显多于正前方（1.3 倍）：第一次转向了镜像，再转 180°（`fixed: "mirror"`）；
   - 峰偏了 10°–150°：再修正一次（`fixed: "corrected"`）；
   - 没再听到声音：只靠看名牌确认。
5. **确认**：取一帧，OCR，找视野中央 ±12° 内的名牌，量它亮没亮（和它的安静样子比，或刚刚 1.5 s 内亮过，回声期的不算）。声音在正前方（或已修正）并且中央名牌亮着（有归属时名字也要对上）才 `confirmed: true`。这一步只是确认：取帧、OCR 失败只记日志、`confirmed: false`，不让整个调用失败，也不因此重置头显连接。全景开着时也一样：眼睛的帧是全景拼块，但 VRChat 的名牌是 UI，画在全景之上、在普通 100° 视图里该在的位置（和 `panolook::overlay_rays` 同一个道理），所以 `centred_plate` 用左眼和眼睛自己的投影找中央 ±12° 的名牌照样对；只是不像 `overlay_rays` 那样用右眼的 UI 遮罩排除拼块里的世界文字（名字要和房间名单匹配，误认很少）。

头显锁只在这一次动作期间持有（和环视、走路一样）；插件对 `/v1/vr/` 路径已经串行。

## 3. 接口

| 接口 | 作用 |
|---|---|
| `/v1/stream`（WebSocket） | 音频帧不变；新增 `speaker` 文本事件（第 1 节） |
| `POST /v1/vr/attend {"pause_s": 8, "since_ms": 4000, "name": "xkeyC"}` | 转向说话的人，三项都可省（第 2.7 节）。回复 `{"ok": true, "name", "user_id", "bearing_deg"（转之前相对头的方位）, "confirmed", "from"（candidate / direction）, "picked"（named / ended / running）, "segment", "residual_deg", "fixed", "plate"}`；没有：`{"ok": false, "reason": "no recent speech"}`；不闲：`{"ok": false, "reason": "busy", "busy": "following" / "moving" / "menu"}` |
| `GET /v1/speakers` | 设置、混音方式、已定位的玩家（方位、名牌高出眼睛多少、距离、多久前、`placed_by`、光环：亮否、高出多少、眼睛和镜头各自的安静样子）、最近 20 段话（归属、置信度、线索、投票的峰、每个候选的分数和 `glow_onset`） |
| `GET /v1/vr/usercam/names?since_ms=10000` | 用户相机的镜头最近读到的名牌（最多 60 s）：名字、相对头的方位（世界、追踪空间、相对头的朝向）、仰角、镜头（orbit / travel）、光环分数、文字框 |
| `POST /v1/speakers/record {"seconds": 60}` | 录一段用于校准（1–600 s，第 4 节），立即返回目录；`{"stop": true}` 立即结束正在录的 |
| `POST /v1/vr/survey` | 返回的 `candidates`、`players` 加了 `talking`（4 s 内被归属说过话） |

参数（`vrc-bridge` 命令行，服务器上写在 `~/.config/vrc-bridge/env` 的 `VRC_BRIDGE_ARGS`）：

| 参数 | 默认 | 作用 |
|---|---|---|
| `--speakers true/false` | true | 说话人追踪；关掉只剩单声道混音 |
| `--hrtf-table` | `auto` | `auto`：二进制所在仓库（`target/release/../../assets/hrtf/`）或当前目录下的 Steam 表，没有就用球形头；`sphere`；或表的路径 |
| `--swap-ears true/false` | false | 采集的左右耳反了（校准 4.2 得出） |
| `--audio-latency-ms` | 60 | 游戏按某个头位姿渲染声音到采集到它的延迟 |
| `--echo-tail-ms` | 400 | bot 的声音播完后还算回声期的时长（第 2.6 节） |
| `--glow-on` / `--glow-off` | 0.30 / 0.15 | 光环分数高出安静样子多少算亮 / 灭（2026-10-08 实测定的） |
| `--glow-release-ms` | 900 | 话说完后光环还亮多久（融合时这段尾巴不算说话） |
| `--doa-only-cap` | 0.55 | 名牌没看到亮、只有方向支持的候选最多这么大的概率，其余给"不认识"（第 2.5 节） |

## 4. 校准（要真人配合）

录制目录在 token 旁边的 `speakers/rec-<unix 毫秒>/`。录制有自己的写文件线程：分析线程和视觉线程只把要写的东西（和名牌截图的像素）交给它，JPEG 编码和写文件都在那个线程里，不占状态锁。

| 文件 | 内容 |
|---|---|
| `audio.wav` | 两耳，float32 48 kHz；开头是录制前环形缓冲里的音频（`meta.json` 的 `preroll_s`，最多 8 s） |
| `hops.jsonl` | 每 10 ms 一行：时间（相对录制开始，秒）、客户端时钟、电平、噪声底、语音频带占比、有声/语音中、是否回声期、头的偏航、GCC 时差和可信度、有效频点数、投票的前两个峰、所在段 |
| `votes.f32` | 每 10 ms 一行 180 个 float32：以头为参照的投票（-180° 起每 2°；无声帧全 0） |
| `glow.jsonl` | 每次量名牌一行：名字、来源（ocr：OCR + 深度定位；read：只 OCR（D42 以前）；projected：投影；orbit：用户相机的镜头读到；lens：镜头转向说话的人时两次读之间重新量）、统计（`ring`、`chroma`、`value`、`ripple`、`hue`、`edges`、`score`）、这个来源的安静样子、高出多少、亮否、是否 bot 回声期、文字框、截图文件 |
| `crops/` | 眼睛里每次量名牌的截图（胶囊和两侧的波纹，外加 1 个字高的边） |
| `segments.json`、`meta.json` | 这期间的语音段和归属；设置 |

### 4.1 名牌光环

2026-10-08 已经录过一次（朋友的名牌，2–3 m，第 2.3 节的数字就是这次的）。录像的两张截图（不亮、金色光环）裁成小图放在 `crates/vrc-bridge/tests/data/` 当测试数据；完整的录像（`big.raw`：1801 张 700×400 的截图，`series.csv`：每张的参考值和名牌位置）在本机时，`VRC_GLOW_RECORDING=<目录> cargo test -p vrc-bridge recorded_series -- --nocapture` 逐帧复测（没有就跳过）。还要补的：

1. 非好友的青色光环、VRC+ 的名牌、5 m 外和视野边缘的名牌：同样的做法，朋友站好、bot 不跟随，`POST /v1/speakers/record {"seconds": 60}`，"安静 10 s → 说话 10 s"交替三轮。
2. 用户相机画面里的名牌（字高只有十几个像素）：开着环绕录，看 `glow.jsonl` 里 `orbit` 来源的分数，安静和说话分得开不开。
3. 看 `glow.jsonl` 和 `crops/`：胶囊的比例（`PILL_*` 常量）、`--glow-on`、`--glow-off`、`--glow-release-ms` 要不要改；镜子里的名牌会不会亮。

### 4.2 方向：转一圈

1. 声源固定不动：朋友站在 bot 旁边 2 m 持续朗读（或世界里一个固定的音源），中途不要走动。
2. 在服务器上 `sudo sh tools/agent-vr/doa_sweep.sh`（默认每步 1°、每步停 1 s，转一圈共约 6 分钟；`STEP=2 HOLD=0.5` 更快）。脚本先停跟随，按最长时长（600 s）开始录制，再用 `/v1/step {"turn": 1}` 一步步转，最后一步停够之后（或被 Ctrl-C 打断时）用 `{"stop": true}` 结束录制；估计转一圈会超过 590 s 时先警告。结束后记得重新跟随。
3. 把录制目录拷回来：`python3 tools/agent-vr/doa_sweep_report.py <目录> --table assets/hrtf/steam-default-48k.bin --table <nearest 表>`（nearest 表用 `hrtf-render --interp nearest --az-step 1 --el-min 0 --el-max 0` 生成）。看：
   - **声道顺序**：面向声源时，头往右转，时差应当从正变负（报告里的 `falling`）。如果面向声源处是 `rising`，说明左右反了：加 `--swap-ears true`。
   - **nearest 还是 bilinear**：时差随头的角度是平滑曲线（bilinear）还是阶梯（nearest，阶梯宽度就是默认 HRTF 的网格）；哪张表的均方根误差小。如果是 nearest，`/v1/vr/attend` 的修正转向要大于一个网格，模板也换成 nearest 表。
   - **是不是默认 HRTF**：最好的那张表，误差应在 1–2 个样本以内；远大于此说明 VRChat 不是用默认 HRTF，或者有 spatialBlend < 1（时差整体偏小）。
4. 顺带量**音频延迟**：快速转一次 90°（`/v1/step {"turn": 90}`），在 `hops.jsonl` 里看时差在头转过之后多久才变：这就是 `--audio-latency-ms`。

### 4.3 语音锚点的高度

- 声音挂在头骨上，名牌也随头骨，但名牌在头顶上方。模板现在只用水平面（仰角 0），近处或高低差大时侧向角会偏（侧向角 = asin(sin 方位 × cos 仰角)）。
- 做法：朋友站在 bot 正右方 0.8 m，持续朗读；bot 用 `/v1/vr/height` 把头的高度从 1.3 m 调到 1.8 m，每档录 10 s。`GET /v1/speakers` 里该玩家的 `rise_m`、`distance_m` 是名牌相对眼睛的高度和水平距离。
- 用每档的时差反推声源的仰角，和名牌的仰角比：两者之差就是"名牌高出声音多少"。这个偏移以后给按仰角选模板的候选评分用（现在还没用上）。

## 5. HRTF 表（`tools/hrtf-render`）

- Steam Audio 的默认 HRTF 不公开（只编进了发行的 `phonon` 库），但可以通过 API 渲染出来：
  - 上下文 48 kHz、帧长 1024；`iplHRTFCreate(IPL_HRTFTYPE_DEFAULT)`，音量 1，不归一化；
  - 每个方向：重置效果器，先在该方向送两帧静音（没有从别的方向渐变过来的残留），再送单位冲激和两帧尾巴，`iplBinauralEffectApply`（spatialBlend 1，bilinear 或 nearest）；输出就是这个方向的左右 HRIR，API 还给出两耳的峰值延迟。
- 只加载 SDK 预编译的库（运行时用 libloading 加载），SDK 里别的东西都不用：

```sh
cargo run --release -p hrtf-render -- --phonon <steamaudio>/lib/windows-x64/phonon.dll \
    --out assets/hrtf/steam-default-48k.bin            # 默认 bilinear，方位每 2°，仰角 -30..60 每 10°
```

- 本机（Windows，SDK 4.8.1，`P:\Astrbot\voice\downloads\steam-audio-4.8.1\`）实测：
  - 冲激在输出里延迟 256 个样本出现，所有方向的 HRIR 在 256 个样本内，存 256 抽头；1800 个方向，文件 1.86 MB。
  - **API 的 `peakDelays` 单位是秒**（不是样本）：正右方左耳比右耳晚 0.65 ms，和互相关量出的一致。
  - 正前方并不完全对称（1 kHz 电平差 2 dB，4 kHz -7.7 dB）：前后的频谱差就是靠这个分。
- 文件格式 `VRCHRTF1`（小端，`crates/vrc-audio/src/table.rs`）：

| 偏移 | 内容 |
|---|---|
| 0 | `"VRCHRTF1"` |
| 8 | u32 采样率 |
| 12 | u32 抽头数 |
| 16 | u32 仰角个数、u32 方位个数 |
| 24 | f32 第一个仰角、仰角步长、第一个方位、方位步长（度） |
| 40 | u32 渲染时的插值（0 nearest，1 bilinear） |
| 44 | f32 缩放：样本 = i16 × 缩放 |
| 48 | u32 Steam Audio 版本（major<<16 \| minor<<8 \| patch） |
| 52 | 填 0 到 64 |
| 64 起 | 每个方向（仰角在外层）：f32 左、右峰值延迟（秒）；i16 左 HRIR；i16 右 HRIR |

方位 0 是正前方，向右为正；仰角向上为正。

- **许可**：`steam-default-48k.bin` 是从 Valve 的 Steam Audio（Apache-2.0）的默认 HRTF 派生的数据，不在仓库的 AGPL 范围内；来历、修改方式、版权声明（含稳妥起见附上的 CIPIC 声明）见 `assets/hrtf/README.md`，许可证全文在 `assets/hrtf/LICENSE-Apache-2.0`。重新生成表时这两个文件要一起更新。

## 6. 没验证的、待定的

- 全部只在合成信号上测过；VRChat 是否真用默认 HRTF、插值方式、声道顺序、音频延迟都要 4.2 的扫描来定。
- 光环只量过一个好友的名牌（4.1）：青色、VRC+、远处、用户相机画面里的都还没实测；`/usercamera/Zoom` 是不是竖直视场也没验证。
- 用户相机的镜头一圈里每个名牌只在画面里一部分时间，光环看得稀疏；有人说话时让镜头停下来看他，还没做。
- 模板只用仰角 0；候选的仰角（名牌高度）还没用上（4.3）。
- 音乐、视频播放器这类持续的空间化声源：检测器会把有语音频带特征的音乐当成语音，投票会出现一个不动的峰。还没做"背景声源图"（研究笔记里的做法：没人说话时也累计直方图，扣掉持续存在的峰）。
- 多人同时说话：直方图能出两个峰，但一段话只归给一个人。
- 玩家走动时，候选位置靠最近一次定位；不说话、不在视野里的人位置会过时。
- 镜子里的名牌可能被当成候选（研究笔记的老问题）。
- **已知限制：Codex 丢输入音频帧会让标签整体偏晚。** Codex 的实时会话把输入音频放进一个 256 帧的队列（AstrBot 每帧 20 ms，约 5 s），满了用 `try_send` 直接丢帧，只在 Codex 的日志里记一条 `dropping input audio frame due to full queue`，不报给 AstrBot。AstrBot 按自己送出的样本数（`sent`）把标签换算到 infra 的时钟，丢掉的帧 infra 没收到，于是之后的标签都比 infra 的 VAD 时钟晚了丢掉的那么多，直到会话重开。只有 Codex 那边卡住 5 s 以上才会发生，很少见；不改 Codex 的行为。要发现它，看 Codex 日志里有没有这条警告。
